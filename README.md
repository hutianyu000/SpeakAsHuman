# SpeakAsHuman

SpeakAsHuman 是一个默认用于中文和英文表达的 Codex skill，覆盖日常回复、起草、润色、审阅、代码命名和注释。

它要求根据目的、受众和上下文处理表达，同时保留原文的数量、条件、否定、归属和不确定性。修改应解决具体问题；已经合适的表达可以保留。

## 适用场景

| 场景 | 处理重点 |
| --- | --- |
| 文章起草与润色 | 组织信息、改善措辞与衔接，保留作者立场和必要限定 |
| 对话与工作消息 | 回答实际问题，说明判断依据，准确表达请求、承诺和进度 |
| 表达审阅 | 定位问题并说明影响，区分规则违规、内容问题、证据缺口和风格偏好 |
| 代码命名 | 根据稳定的职责、领域概念和实际行为选择名称 |
| 注释与技术说明 | 说明有依据的原因、约束和接口行为，避免重复代码或加入未经确认的解释 |
| 中英文混合内容 | 分别处理正文、术语和标识符，遵循各自的语言与项目约定 |

## 安装

先在选定的本地工作目录克隆仓库：

```bash
git clone https://github.com/hutianyu000/SpeakAsHuman.git
```

将仓库中的完整 `speak-as-human/` 目录复制到当前 Codex 配置的技能目录。使用 `CODEX_HOME` 的环境，对应路径为 `$CODEX_HOME/skills/speak-as-human/`。保留 `SKILL.md`、`agents/` 和整个 `references/` 目录，确保调用配置与参考文件齐全。

完成后，确认 Codex 的可用技能列表中出现 `speak-as-human`。安装位置应以当前环境的配置为准。

## 使用

不必在每次请求中点名技能。提供目标文本、用途和需要保留的内容即可；也可以用 `$speak-as-human` 显式调用。

起草或润色：

```text
请润色下面这封工作邮件。
面向项目负责人，保持正式、直接，保留原有日期、承诺和不确定性。
```

表达审阅：

```text
请审阅下面的段落。
指出影响理解或改变结论的问题，并说明依据。先不要修改原文。
```

命名与注释：

```text
请检查这个函数的名称和注释。
结合实现与直接调用判断是否准确，只提出建议，不执行重命名。
```

技能加载后，规则默认适用于日常回复和任务中的表达，包括进度说明、文章、消息、命名和注释。用户可以要求关闭技能或为某项任务指定其他风格。开发任务中的应用范围限于本任务新建或修改的表达，不因此重写旧注释、执行额外重命名或扩大实现范围。

## 默认适用与实际加载

默认适用是技能的表达策略，实际加载由 Codex 决定。`SKILL.md` 的发现描述说明适用范围，`agents/openai.yaml` 中的 `allow_implicit_invocation: true` 允许自动调用，无需用户显式指定。它不保证每轮都加载，也不会把技能变成常驻的系统提示。

如果希望每个会话都固定加载，可以在全局或项目 `AGENTS.md` 中加入宿主规则：

```text
每个会话开始时，查找已安装的 speak-as-human，读取其 SKILL.md。
默认将规则用于当前回复和任务中的表达，按需读取参考文件；
规则未变时复用已加载的内容，无需每轮重复读取。
用户要求关闭或指定其他表达方式时，遵循用户要求。
默认启用不扩大文件编辑、内容重组或重命名的授权范围。
```

这是确保加载的宿主配置。安装技能本身不会修改 `AGENTS.md`。默认适用不要求显式调用，也不扩大文件编辑权限。

## 表达规则与修改边界

- 保留语义和证据状态。润色不得把可能改成确定、删掉适用条件，或把输入中的陈述包装成已经核验的研究结果。
- 根据内容判断措辞。对比、重复、限定语和专业术语有实际作用时可以保留，不按固定句式或词语名单机械删除。
- 按语言和功能处理标点。中文正文禁止句子破折号；英文中有实际作用或符合目标文体的用法可以保留。双引号可以标记引语、名称、标签、特殊词义或正在讨论的措辞，不要求所标表达一定是正式定义的术语，也不能用来制造虚假引用、对立或概念依据。
- 避免虚构对立、无依据的强化和意图归属。技术简称应对应已知行为，不能凭空加入动机、故障原因或验证状态。
- 保护精确内容。代码语法、命令、路径、标识符、数学符号、引用键及要求逐字保留的材料，应遵守各自的契约。
- 遵守授权范围。语言润色不自动授权内容重组；审阅不自动授权修改文件；命名建议不自动授权执行重命名。

完整要求见 [SKILL.md](speak-as-human/SKILL.md)。这些约束也适用于交付说明和新写的自然语言注释；代码中的语法字符及精确内容有独立的保护边界。

## 评估与维护

评价一次修改时，检查它是否解决了具体问题，是否造成不必要的改写，以及是否丢失数量、条件、否定、归属或不确定性。标点合规、清晰度、自然程度和作者风格应分别判断。

修订技能时，使用相同输入比较候选版与旧版或未启用技能的基线，同时包含需要修复的文本和本来就合适的文本。示例说明预期边界，不能单独证明实际效果，也不应作为要求逐字复现的答案模板。

更详细的方法见 [evaluation.md](speak-as-human/references/evaluation.md)。表达审阅不等于事实核验、科学论证验证或工程行为测试；需要这些检查时，应根据任务另行执行。
